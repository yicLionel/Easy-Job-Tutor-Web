# Easy Job Tutor 网页主产品设计规格

- 状态：已批准，进入实施
- 日期：2026-07-30
- 首期岗位：AI 产品经理实习与校招
- 首期用户：在校生与应届生

## 1. 一句话产品合同

Easy Job Tutor 不是一个以模板、排版或一键生成简历为中心的工具，而是一个“岗位差距闭环教练”：

> 根据目标 JD 与用户确认过的真实经历，找出最可能阻塞本次求职的少数差距，把每个差距转化为有来源、有限时、可完成、可复测的准备任务。

第一版只服务 AI 产品经理实习与校招。简历优化用于解决“有事实但不会表达”，面试练习用于检查“知识与表达是否达到岗位要求”；两者都是差距闭环中的手段，不建设成互相分离的功能岛。

## 2. 背景与问题

Easy Job Tutor 已经存在两个产品层：

- 开源 Skill 沉淀了 JD 分析、事实状态、五维诊断与真实信息约束。
- Chrome Side Panel MVP 把 JD、简历、确认、诊断、补充事实和改写串成了交互流程。

Side Panel 仍值得保留，但它不适合作为国内普通学生的唯一入口。国内浏览器的 Side Panel 兼容性不一致，商店分发与安装存在额外门槛，当前 MVP 还要求用户理解侧载与模型配置。响应式网页因此成为主产品入口；Side Panel 未来只作为可选 Companion，负责读取当前招聘页面的 JD、显示轻摘要，并打开相应网页工作区。

“粘贴 JD + 上传简历 + 匹配度 + AI 改写”已经是国内 AI 简历产品的基础功能。产品的差异化不能来自功能数量，而要来自以下合同：

1. 用户事实分为 `confirmed`、`pending_confirmation` 与 `model_inference`。
2. 未确认事实不得进入最终简历、面试回答范本或求职结论。
3. 每个关键差距都能追溯到 JD 要求、用户证据和考点来源。
4. 每个准备任务都必须有交付物、完成条件和复测方式。
5. 学习或商业内容不能改变差距本身的优先级。

## 3. 目标与非目标

### 3.1 第一阶段目标

第一阶段要验证的不是“用户是否觉得页面好看”，而是：

- 用户能否在点击分析后 15 秒内获得可信的前三项关键差距和总体判断。
- 用户能否理解每项差距为何重要、当前证据为何不足。
- 用户能否开始并完成至少一个由差距生成的准备任务。
- 完成任务后，用户能否通过复测看到准备状态发生了有依据的变化。
- 相比用户原流程和通用模型一次性提示词，事实闸门能否减少虚构、降低纠错或提高证据可追溯性。

### 3.2 第一阶段不做

以下能力不进入第一版：

- 通用简历模板商城、复杂所见即所得编辑器和 PDF 排版系统。
- 自动投递、批量抓取岗位或代替用户申请职位。
- 语音或视频模拟面试、数字人面试官。
- 多 Agent 协作、开放式互联网实时搜索和用户请求链路中的实时爬取。
- 同时覆盖社招、开发、算法、运营等多个岗位，以及海外求职或多语言内容。
- 复杂账号体系、社交关系、支付、订阅和商家投放后台。
- 由赞助、佣金或广告竞价影响 P0/P1/P2 差距排序。
- 继续扩张 Side Panel；其代码与产品经验保留，但不属于本阶段交付。

## 4. 用户、使用场景与成功路径

### 4.1 目标用户

首批用户是准备 AI 产品经理实习或校招的在校生与应届生。他们通常已经有一份简历，也找到一个具体 JD，但不知道：

- JD 中哪些要求是核心门槛，哪些只是常见描述。
- 自己的简历是表达不足、证据不足，还是确实存在知识或实践缺口。
- 面试高频考什么，应该先学什么，而不是泛泛地“学习 Agent、RAG”。
- 如何把七天准备时间分配给最有影响且可行动的任务。

### 4.2 核心成功路径

核心路径只有一条：

`进入邀请码 → 粘贴 JD 与上传/粘贴简历 → 确认解析材料 → 15 秒内看到前三项差距 → 展开证据与来源 → 生成七天计划 → 完成任务 → 针对性练习 → 复测 → 更新准备状态`

用户可以退出并恢复，但输入发生改变后，旧分析必须明确失效，不能悄悄混入新结果。

## 5. 信息架构与界面

网页采用一个连续工作台，而不是五个互不相关的 AI 工具入口。

### 5.1 页面

1. **欢迎与邀请码页**
   - 解释产品合同、数据边界和首期适用岗位。
   - 输入邀请码，创建匿名 Beta 会话。
   - 生成一次性展示的恢复码，用户自行保存。

2. **材料输入与确认页**
   - JD 支持粘贴文本。
   - 简历支持 PDF、DOCX 或粘贴文本。
   - 上传文件解析后立即删除原始文件。
   - 页面展示标准化后的 JD 与简历内容，用户确认后才进入分析。
   - 解析失败时必须提供手动粘贴，不阻塞主流程。

3. **差距结果工作台**
   - 页面先展示前三项关键差距和总体判断，随后渐进补充学习计划、来源与复测题。
   - 每项差距显示：优先级、差距类型、影响理由、JD 证据、当前用户证据、考点信号、置信度和下一步。
   - 表达类差距可以生成逐条、文本级的简历修改建议，但不提供模板排版或复杂在线编辑器。
   - 不显示伪精确的录用概率或 ATS 通过概率。
   - 页面显示当前分析版本、输入摘要和生成状态。

4. **七天计划页**
   - 计划只从已识别差距生成。
   - 用户先选择每日可投入的 15、30、60、90 分钟或自定义时长；该设置不阻塞前三项差距生成。
   - 每个任务显示目标、预计时长、推荐资料、来源、交付物、完成条件与复测方式。
   - 用户可以调整每天可用时间，但不能通过调整计划隐藏核心能力缺口。

5. **任务与复测页**
   - 支持知识问答、产品方案题、项目深挖和材料表达任务。
   - 面试题必须绑定 `考点 ID + JD 要求 + 来源事件 + 评测 Rubric`。
   - 完成结果保存为证据；只有用户确认的新增事实才进入事实底稿。
   - 复测展示“哪些证据变强、哪些仍不足”，而不是只改一个分数。

6. **隐私、恢复与删除页**
   - 展示保存的数据类型、模型发送范围、处理时间和删除规则。
   - 输入恢复码找回会话。
   - 支持删除单次分析或整个匿名会话；整会话删除后恢复码失效。

### 5.2 结果呈现原则

总体判断不用单一百分制。第一版采用三个可解释的主判断：

- **主要是表达缺口**：已有相关事实，但简历或回答没有把行动、方法和结果映射到 JD。
- **存在可短期补齐的准备缺口**：关键知识、案例或表达练习不足，可在七天任务中形成证据。
- **存在核心能力或经历缺口**：岗位硬要求缺少可核验经历，短期学习不能被包装成项目经验。

同一用户可以同时存在三类问题。页面以影响最大的类型作为总体判断，并列出触发依据。这个判断不代表录用概率。

## 6. 差距模型与排序合同

### 6.1 输入

差距分析只使用：

- 用户确认的 JD 标准化文本。
- 用户确认的简历文本与事实底稿。
- 版本化 AI 产品经理能力 taxonomy。
- 版本化、人工审核的面经考点快照。
- 当前分析中用户确认的补充信息。

未经确认的模型推断可以用于追问，但不能作为“用户已经具备”的证据。

### 6.2 差距类型

每项差距必须属于一种主类型：

- `evidence_expression`：真实事实存在，但表达或映射不足。
- `knowledge`：知识或技术判断不足。
- `product_case`：缺少可讲清的产品决策、评测或复盘案例。
- `interview_expression`：知道内容但无法稳定、结构化地回答。
- `core_experience`：缺少岗位硬要求对应的真实经历。

### 6.3 影响度与可行动性分离

为了避免“七天能补”反而排在“真正重要”之前，系统分别计算：

- **影响度**：JD 重要性、独立面试事件频次、证据缺口程度与来源置信度。
- **可行动性**：预计准备时间、是否存在可完成交付物、是否能在当前周期复测。

优先级首先由影响度决定：

- `P0`：JD 硬要求没有证据，或高置信高频核心能力存在明显缺口。
- `P1`：重要但不是硬门槛的差距，或现有证据质量不足。
- `P2`：优化项、低频项或对本次 JD 影响较小的差距。

可行动性只决定任务怎么排，不降低不可短期解决的 P0。核心经历缺口必须明确写“七天内不能替代真实经历”，同时可以提供诚实的替代动作，例如补做窄场景验证、完善现有项目证据或调整投递预期。

### 6.4 可解释性

每项差距都保存组成信号，不只保存最终优先级。用户可以看到：

- 对应 JD 原句或标准化要求。
- 简历中匹配、部分匹配或缺失的证据。
- 支持该考点的独立事件数量、平台分布、时间窗和置信度。
- 该差距为何进入前三，以及为何不是更高或更低级别。

前三项差距是强制可追溯对象。完整阶段结束时，每一项都必须绑定 JD 要求、用户的已确认事实或明确证据缺口、考点 ID、来源样本与置信度、至少一个准备任务和一个复测条件；任一关系缺失时，该项不能标记为完整。

## 7. 高频考点语料合同

### 7.1 来源角色

官方 JD 与官方技术问答用于定义能力 taxonomy 和知识基准，不直接代表面试频次。牛客、小红书、知乎等社区来源用于观察实际面试事件、题目主题与上下文。

### 7.2 第一版采样

- 主时间窗为最近 12 个月。
- 牛客、小红书、知乎每个平台最多采集 20 篇候选帖子。
- 12 至 24 个月内容只作为降权补充；更早内容不进入当前高频榜。
- 热度只用于候选采集顺序，不直接等于面试频率。
- 帖子拆成独立面试事件；跨平台搬运、转载和同一事件重复发布只计一次。
- 高频信号由去重事件数、来源多样性和时间衰减共同形成。

### 7.3 内容存储与展示

运行时只读取人工审核、版本化的离线快照，不实时抓取平台。每条事件至少包含：

- 公司、岗位、轮次、面试时间或发布日期。
- 结构化考点、简短转述和来源 URL。
- 平台、固定查询词、采集日期、证据等级、重复事件标识。
- 许可与展示状态。

产品默认保存结构化转述，不复制大段原文。用户侧展示原始链接、采集日期、样本量和置信度。来源不可访问时显示状态，不删除历史来源字段，也不把无法访问自动解释为内容失实。

### 7.4 内容发布闸门

快照发布前必须完成：

- 重复事件审核。
- 营销软文与培训广告降权。
- 题目主题与 taxonomy 映射复核。
- 来源 URL 和日期抽样验证。
- 全量结构化内容人工检查。

代码测试通过不能替代内容审核。

## 8. 七天任务与复测合同

每个任务必须绑定一个或多个 `gap_id`，并具备：

- `objective`：完成后应增加什么证据。
- `estimated_minutes`：真实时间预算。
- `resource_refs`：来源、适用理由与免费替代。
- `deliverable`：可检查的产出，例如一页 Agent 方案、十条评测集或两分钟项目回答。
- `completion_rule`：何时可以标记完成。
- `retest_rubric`：用什么标准复测。

仅阅读资料不能自动判定差距已补齐。任务完成后至少需要一次产出、回答或可核验材料。复测可以提高“知识准备”或“表达准备”状态，但不能自动把练习结果写成真实工作经历。

## 9. 商业内容边界

未来可以接入书籍、课程或学习材料推广，但商业内容与诊断排序严格分离：

- 赞助不得改变差距影响度、P0/P1/P2 或进入前三的顺序。
- 商业资料必须显式标记“推广/赞助”。
- 必须说明推荐理由、适用对象和免费替代。
- 同一任务先确定学习目标，再从满足目标的资料中展示自然结果与商业结果。
- 第一版不实现商家后台、竞价、支付或佣金结算。

在真实用户尚未完成任务并产生复测数据前，商业化只是后续假设，不作为产品价值证据。

## 10. 系统构型

### 10.1 总体架构

第一版采用模块化 Next.js/TypeScript 单体，保留清晰的模块与端口边界：

```text
Browser UI
  ├─ Material Intake
  ├─ Gap Workspace
  ├─ Seven-day Plan
  └─ Task & Retest
          │
Next.js API / Analysis Orchestrator
  ├─ Session & Invite
  ├─ Document Parser
  ├─ Fact Ledger
  ├─ Gap Engine
  ├─ Plan Engine
  ├─ Retest Engine
  ├─ Model Adapter
  └─ Event Stream
          │
Persistent Store + Versioned Corpus Snapshot

Offline Corpus Pipeline
  ├─ Candidate Collection
  ├─ Event Normalization
  ├─ Deduplication
  ├─ Human Review
  └─ Snapshot Publish
```

用户分析链路与语料采集管线完全分离。用户请求不得等待平台搜索、抓取或人工审核。

### 10.2 模块边界

- `session`：邀请码、匿名会话、恢复码、删除与配额。
- `materials`：JD/简历输入、解析、标准化、确认和输入版本。
- `facts`：事实状态、来源、证据和确认历史。
- `corpus`：只读 taxonomy 与版本化考点快照。
- `analysis`：快速差距、完整差距、信号与优先级。
- `plans`：七天任务、时间预算和任务依赖。
- `practice`：问题、回答、Rubric 与复测。
- `ai`：供应商无关的结构化模型适配器、超时、重试和安全输出校验。
- `events`：分析阶段事件、SSE 订阅和重连恢复。

每个模块通过类型化服务接口使用，不允许 UI 直接访问数据库，也不允许模型适配器直接修改事实底稿。

### 10.3 持久化策略

第一版使用单实例持久化数据库，数据访问通过 repository 接口隔离。闭测规模为 8 至 15 名用户，优先保证简单、可恢复和可测试；未来多实例部署时可以迁移数据库实现，而不改变领域接口。

需要持久化：

- 匿名会话、邀请码使用状态和恢复码摘要。
- 已确认材料、事实底稿、分析版本和结果。
- 计划、任务状态、练习回答和复测记录。
- 内容快照版本与来源元数据。
- 最小化的产品事件和性能指标。

原始 PDF/DOCX 不持久化。

## 11. 15 秒渐进分析

### 11.1 时间合同

`time_to_first_insight` 从用户点击“开始分析”时起算。材料或会话校验失败必须立即返回错误；有效请求不得通过延迟发送或延迟“接受”来缩短计时。计时到页面首次稳定展示以下全部内容时结束：

- 三项真实生成的关键差距。
- 每项差距的优先级和一句影响理由。
- 一个可解释的总体判断。

封闭 Beta 在约定设备、网络与并发配置下的硬门槛是：所有有效测试请求均在 15 秒内展示上述真实结果，且 `p95 <= 12 秒`。断网等用户侧不可用时间单独记录，不纳入服务计算时延，但页面一旦恢复连接必须从已持久化状态继续。页面不能用空白、纯转圈、随机占位或虚假百分比冒充结果。

`time_to_complete_report` 单独记录，不受 15 秒硬门槛约束，但所有后续阶段必须显示真实状态。

### 11.2 两阶段计算

快速阶段只使用：

- 标准化 JD 要求。
- 确认后的事实底稿。
- 离线 taxonomy 与考点快照。
- 一次受限、可超时的结构化模型调用。

确定性差距计算与模型调用并行开始。模型的快速阶段硬预算不超过 8 秒；服务端最迟在第 12 秒持久化 `fast_insight_ready`，为传输与渲染预留 3 秒。若模型未在预算内返回，差距引擎使用确定性信号输出降级版前三项，并明确标记“初步结果”；模型结果随后只能补充解释，不能无提示地完全改写优先级。

完整阶段渐进生成：

- 详细证据映射。
- 七天任务。
- 来源与置信度。
- 面试练习与复测 Rubric。

### 11.3 事件协议

分析事件至少包含：

- `analysis_id`
- `request_id`
- `input_version`
- `stage`
- `status`
- `occurred_at`
- `payload`

阶段包括 `accepted`、`fast_insight_ready`、`evidence_ready`、`plan_ready`、`practice_ready`、`complete`、`failed`。

SSE 不是首个结果的唯一交付路径。连接异常时，客户端通过同一 `analysis_id` 轮询已持久化阶段，保证网络仍可用但流连接失败时不突破 15 秒门槛。SSE 恢复后再从最后事件序号继续，不得因为重连或轮询重复创建分析。

## 12. 并发、版本与过期结果

每次材料确认都会生成新的 `input_version`。每次分析都有唯一 `request_id` 和 `analysis_id`。

- 同一会话可以有多个历史分析，但只有与当前 `input_version` 一致的结果可标记为当前。
- 用户修改 JD、简历或事实后，旧分析立即显示“基于旧材料”，不能覆盖新工作区。
- 写入分析阶段前必须检查 `input_version`。
- 相同幂等键的重复提交返回已有分析，不创建重复任务。
- 不使用全局 LLM 锁；并发通过请求级超时、速率限制和模型适配器并发上限管理。

## 13. 模型使用边界

第一版由平台通过服务端模型适配器统一调用模型，不要求学生自备 API Key。供应商与具体模型名称不进入领域层。

模型适合：

- 把 JD 与简历解析成待确认的结构化候选。
- 生成差距解释、追问和任务草稿。
- 在已绑定来源与 Rubric 的条件下生成练习题变体。
- 对用户回答生成结构化评审建议。

模型不得：

- 把未确认推断写成用户事实。
- 自行创建来源或伪造面试频次。
- 直接修改 P0/P1/P2 而不返回组成信号。
- 把练习表现改写成真实经历。
- 输出录用概率、ATS 通过率或未经校准的招聘预测。

所有模型输出必须通过 schema 校验、来源引用检查与事实状态检查。失败时进入可解释的降级或重试状态。

## 14. 匿名 Beta、隐私与安全

第一版使用“邀请码 + 浏览器会话 + 恢复码”，不建设用户名密码系统：

- 邀请码限制使用次数和有效期。
- 浏览器获得 `HttpOnly`、`Secure`、`SameSite=Lax` 的不透明会话 Cookie。
- 恢复码只在创建时完整展示；数据库仅保存安全摘要。
- 用户可以生成新的恢复码；新码生效后旧码立即作废。删除会话时所有恢复码摘要同时失效。
- API 进行请求体大小、文件类型、文件签名、速率与并发限制。
- 日志不得记录简历正文、恢复码、模型密钥或完整模型请求。

用户上传 PDF/DOCX 后：

1. 在受限临时空间解析。
2. 生成标准化文本候选。
3. 删除原始文件。
4. 等待用户确认标准化内容。

隐私页必须明确展示哪些标准化文本会发送给第三方模型、为什么发送、保留多久，以及如何删除。用户删除整个会话后，业务数据、恢复能力与关联分析都失效；仅保留不含正文且无法回连个人的聚合运行指标。

## 15. 错误与恢复

- **文件解析失败**：保留 JD，提示失败原因并切换到粘贴文本。
- **模型超时**：保留确定性快速差距，标记降级，允许重试完整分析。
- **完整阶段失败**：已经生成的前三项差距不消失，失败阶段可单独重试。
- **网络/SSE 中断**：从持久化状态恢复，不重复提交。
- **输入已变化**：旧结果保留为历史，当前页阻止其写回。
- **来源链接失效**：显示最近核验时间与不可访问状态，保留来源元数据。
- **数据库写入失败**：不得先向 UI 宣告成功；只有持久化完成后发送阶段完成事件。
- **删除失败**：页面不得假成功，显示可重试状态和事件编号。

任何错误提示都要说明“哪些结果仍然可信、哪些尚未完成、用户下一步能做什么”。

## 17. 产品事件与验证指标

第一版只采集验证核心闭环所需的最小事件：

- 材料开始、解析成功/失败、材料确认。
- 分析接受、首个结果展示、完整结果完成/失败。
- 差距展开、任务开始、任务完成、复测开始和复测完成。
- 用户纠正模型提取、否认推断、编辑建议和删除数据。

关键指标：

- `time_to_first_insight` 的 p50/p95。
- 材料确认到前三项差距的任务完成率。
- 最终关键陈述的虚构事实率。
- 证据可追溯率。
- 用户纠正次数与人工纠错时长。
- 建议接受率。
- 首个任务开始率与完成率。
- 复测完成率。
- 14 日内第二个 JD 或第二次任务的复用率。

Beta 对照至少包含：

1. 用户原有流程。
2. 通用模型一次性 Prompt。
3. Easy Job Tutor 事实闸门与差距闭环。

样本量为 8 至 15 名时，只报告探索性结果、样本与限制，不声称证明求职成功率。

## 18. 测试策略

### 18.1 单元测试

必须覆盖：

- 未确认事实不能进入最终材料。
- 差距类型分类与 P0/P1/P2 规则。
- 影响度与可行动性独立计算。
- 独立面试事件去重、平台平衡和时间衰减。
- 来源字段、快照版本和失效状态保留。
- 七天任务必须具备 gap、交付物、完成条件与复测 Rubric。
- 输入版本变化后旧响应不能写回。
- 幂等提交不能创建重复分析。
- 模型 schema、来源和事实状态校验。
- 恢复码摘要校验与删除后失效。

### 18.2 集成测试

必须覆盖：

- 邀请码 → 匿名会话 → 恢复会话。
- JD/简历 → 解析 → 用户确认 → 事实底稿。
- 快速差距 → 完整证据 → 七天计划 → 任务 → 复测。
- 模型超时后的确定性降级。
- SSE 重连后的状态恢复。
- 文件删除、业务删除和恢复码失效。
- 数据库写入失败时 UI 不出现假成功。

### 18.3 端到端测试

真实浏览器至少验证：

- 正常完整路径。
- PDF/DOCX 解析失败后粘贴恢复。
- 快速模型超时仍在时限内展示可用差距。
- 分析过程中刷新或断网后恢复。
- 修改输入后旧结果不会覆盖新结果。
- 删除单次分析与删除整个会话。
- 移动端与桌面端核心路径可完成。

### 18.4 性能测试

在与闭测相同的模型、数据和并发配置下，使用真实请求测量：

- 所有受控有效请求 `time_to_first_insight <= 15 秒`，且 `p95 <= 12 秒`。
- 超时时页面展示的是真实降级结果，不是占位。
- 并发用户之间不会因全局锁互相串行阻塞。

如果性能门槛未通过，不通过缩短文案或伪造进度规避，必须减少快速路径工作量、缓存版本化内容或改进调用策略。

### 18.5 内容评测

建立 30 至 50 份匿名或合成但明确标注的 AI 产品经理 JD/简历用例，由人工审核：

- 前三项差距是否与 JD 和材料一致。
- 是否把表达缺口误判为经历缺口，或反之。
- 是否引用了真实、相关的来源信号。
- 任务是否能在预计时间内完成并形成产出。
- 复测是否只提升被实际验证的状态。

至少两名熟悉 AI 产品招聘、面试或岗位要求的评审者独立检查差距相关性与优先级；分歧必须记录并进入规则或语料复核，不能由模型自动裁决。

内容评测不以“模型回答看起来合理”为通过标准。

## 19. 视觉与交互方向

视觉应表现“审慎、可信、能行动”，不模仿模板商城或聊天机器人。

- 桌面端以单一工作台为主，左侧展示当前材料与分析版本，中间承载差距和任务，右侧按需展开证据与来源。
- 移动端按“判断 → 差距 → 下一步”顺序折叠，不强行复制三栏。
- 使用清晰的层级、充足留白和克制色彩；P0/P1/P2 不能只依赖红黄绿，需要文字与图形双重编码。
- 来源、置信度、事实状态和历史版本要清晰但不喧宾夺主。
- 生成状态使用阶段名称和已经完成的真实内容，不使用虚假百分比进度条。
- 不把所有功能做成同样权重的卡片墙；首屏应把前三项差距和第一个行动突出出来。

具体字体、色板、间距、动效和组件规范在实施计划的视觉工作包中确定，但不得改变本规格的信息优先级。
