> 文档类型：内部执行基线（Product Delivery Baseline）
>
> 产品负责人：项目所有者
>
> 执行方式：单一人工负责人 + 多 Agent 协作
>
> 目标发布日期：2026-08-16 前完成 Go/No-Go 评审
>
> 文档版本：v1.0
>
> 文档状态：已确认，可进入实施计划阶段
>
> 适用范围：Easy Job Tutor Web，不包含浏览器扩展和 Skill 安装包

## 1. 执行摘要

### 1.1 产品目标

在一周内将 Easy Job Tutor Web 从“已部署的功能原型”推进为任何用户均可访问的公开 Beta。公开 Beta 必须能够安全处理真实简历，清楚说明能力边界，并具备监控、反馈、限流和回滚能力。

本周期不以功能数量为成功标准。唯一需要做深、做可信的核心闭环是：

> 用户输入一个岗位 JD 和一份简历 → 系统拆解岗位要求 → 定位简历原文证据 → 标出缺口与不确定项 → 生成事实保护型修改建议 → 用户确认或修改 → 导出简历草稿。

### 1.2 对外产品定位

Easy Job Tutor Web 是面向在校生和应届生的求职辅助工具。公开 Beta 输出的是：

- JD 要求拆解；
- 简历关键词覆盖情况；
- 可追溯到简历原文的证据；
- 能力缺口和不确定项；
- 不编造候选人事实的修改草稿。

公开 Beta 不声称：

- 预测录用概率；
- 代表招聘方或 ATS 的真实评分；
- 证明候选人具备某项能力；
- 判断简历事实是否真实；
- 保证获得面试或 Offer。

### 1.3 首发范围

#### 必须上线

- 中文 Web 版；
- 单 JD + 单份简历完整分析；
- PDF、DOCX、TXT 文件解析；
- JD 必需项、加分项和未知项拆解；
- 简历原文证据定位；
- 关键词覆盖、缺口和不确定项；
- 事实保护型 Bullet 修改建议；
- 用户确认、修改、拒绝建议；
- Markdown 草稿导出；
- 上传前隐私提示和用户同意；
- 移动端与桌面端可用；
- 文件限制、限流、超时和结构化错误；
- 核心埋点、错误监控、健康检查和回滚方案；
- 公开 Beta 标识、隐私说明、使用条款和反馈入口。

#### 本周期隐藏或降级

- 多 JD 对比；
- 学习路线；
- 模拟面试；
- 完整英文版；
- 账号、云端历史记录和跨设备同步；
- OCR；
- PDF/DOCX 成品简历导出；
- 付费；
- “可信度”“录用概率”“面试准备度”等未经验证的评分；
- 无法说明计算依据的综合分。

### 1.4 一周上线原则

1. 一周是目标，不是绕过质量闸门的理由。
2. 任何 P0 未解决，产品负责人必须选择延迟、降级或缩小流量，不能自动公开。
3. 开发 Agent 不得验收自己的工作。
4. 所有分析结论必须区分“有证据”“不确定”“未发现证据”。
5. 所有新增数字、职责和成果必须由用户确认。
6. 原始 JD、简历正文、姓名、邮箱和电话不得进入埋点及错误监控。
7. 上线后必须有人类产品负责人保持决策与回滚权限。

## 2. 当前状态与问题基线

### 2.1 已具备能力

- Web 首页和核心 API 已部署；
- JD 拆解与 JD + 简历完整分析链路可返回结果；
- 支持 PDF、DOCX、TXT 文本解析；
- 具备三类 AI 岗位知识库；
- 具备关键词权重、差距清单、学习建议和 Markdown 导出基础；
- 工作区正在增加 JD 定向技能筛选和事实保护型简历草稿；
- 已有少量解析与 matcher 单元测试。

### 2.2 当前 P0

| 编号 | 问题 | 用户后果 | 本周期处置 |
|---|---|---|---|
| P0-01 | 否定表达和关键词堆砌可获得高分 | 用户被错误高分误导 | 取消权威综合分；增加否定、上下文和对抗测试 |
| P0-02 | “可信度”“HR 扫描体验”等指标超出算法能力 | 形成虚假权威感 | 删除或改为可解释的结构检查项 |
| P0-03 | 390px 移动端侧边栏遮挡正文并横向溢出 | 大量移动用户无法完成分析 | 修复 Vue 根节点 class 绑定并完成真机/E2E 验证 |
| P0-04 | “离线可用、无第三方上传”与 Web 数据流不一致 | 隐私误导 | 重写对外文案并上线隐私说明和上传同意 |
| P0-05 | 上传没有应用层文件大小、页数、真实类型和解压限制 | 可被超大或恶意文件拖垮 | 前后端双层限制，拒绝不支持文件 |
| P0-06 | 无错误监控、关键漏斗、反馈和回滚演练 | 公开后无法发现事故或判断价值 | 上线最小监控、埋点、告警和回滚流程 |
| P0-07 | 本地环境与完整测试不可稳定复现 | 发布质量不可证明 | 重建 Python 3.12 环境并加入 CI |

### 2.3 需求假设

#### 核心用户

- 正在进行校招、实习或毕业求职的学生和应届生；
- 需要针对不同公司同类岗位反复调整简历；
- 不熟悉如何把 JD 要求映射到自己的项目经历；
- 担心 AI 为简历编造经历和数据；
- 希望在十分钟内得到可操作的修改建议。

#### 用户任务（JTBD）

> 当我准备投递一个新岗位时，我希望快速理解 JD 真正重视什么，并基于我已有的真实经历调整简历，从而减少逐项对照和重写的时间，同时避免写入无法在面试中解释的内容。

#### 现有替代方案

- 手工逐条对照 JD；
- 复制 JD 和简历给通用大模型；
- 使用传统 ATS 关键词工具；
- 请同学、老师或职业顾问修改；
- 不做针对性调整，直接使用通用简历。

#### 产品差异化假设

产品的潜在差异化不是“再生成一份 AI 文字”，而是：

- 每条判断可回到 JD 与简历原文；
- 清楚区分事实、建议和待确认信息；
- 不自动编造数字和经历；
- 给出可以直接接受、修改或拒绝的 Bullet 草稿；
- 在隐私和成本受控的前提下快速返回。

### 2.4 核心风险假设

- 用户可能把关键词覆盖误解为真实岗位竞争力；
- 规则系统可能错误理解否定表达、熟练程度和上下文；
- 用户可能因隐私担忧拒绝上传真实简历；
- 建议可能正确但不够具体，无法产生导出行为；
- 一周内多 Agent 并行容易产生接口漂移、重复改动和无人负责的集成问题；
- 公开流量可能导致文件解析资源被滥用。

## 3. 成功定义与指标体系

### 3.1 北极星指标

> 有效建议采用率：完成一次分析，并接受、修改或导出至少一条有原文证据支持的建议的用户数 ÷ 分析成功用户数。

该指标同时要求分析完成、建议有证据、用户产生行动，避免只优化访问量或虚假的高分展示。

### 3.2 公开 Beta 首周建议阈值

以下阈值为首版运营闸门，首周数据足够后允许由产品负责人校准，但不得在数据不足时降低安全和事实准确性门槛。

| 维度 | 指标 | 计算口径 | 首周目标/闸门 |
|---|---|---|---|
| 获客 | 首页到开始分析转化率 | 开始分析用户 / 首页独立访客 | ≥ 35% |
| 激活 | 分析成功率 | 分析成功请求 / 合法分析请求 | ≥ 98% |
| 价值 | 有效建议采用率 | 采用、修改或导出建议用户 / 分析成功用户 | ≥ 30% |
| 价值 | 主观有帮助率 | 选择有帮助用户 / 提交反馈用户 | ≥ 70% |
| 留存 | 7 日再次分析率 | 7 日内再次分析用户 / 首次分析用户 | ≥ 15% |
| 质量 | 证据准确率 | 人工标注正确证据数 / 全部系统证据数 | ≥ 95% |
| 质量 | 事实编造率 | 包含未确认新增事实的建议 / 全部建议 | 0% |
| 质量 | 否定表达用例通过率 | 正确识别否定的用例 / 否定测试集 | 100% |
| 稳定性 | 服务端 5xx | 5xx 请求 / 全部请求 | < 1% |
| 性能 | 文本/DOCX p95 | 分析接口 p95 响应时间 | ≤ 8 秒 |
| 性能 | PDF p95 | PDF 分析接口 p95 响应时间 | ≤ 12 秒 |
| 移动端 | 核心流程完成率差异 | 移动端与桌面端完成率差异 | 不超过 15 个百分点 |

### 3.3 反指标

任何优化不得通过以下方式换取增长：

- 用更高分刺激分享；
- 默认勾选隐私同意；
- 把未知项标为已确认；
- 将原始简历上传到分析、埋点或日志第三方；
- 隐藏解析失败和低置信度；
- 自动把待确认内容写入最终导出。

## 4. 阶段一：需求分析（Day 1）

### 4.1 阶段目标

冻结首发用户、核心问题、价值主张、范围和指标，确保所有 Agent 对“做什么”和“不做什么”理解一致。

### 4.2 必须回答的产品问题

1. 用户最需要的是诊断报告，还是可以直接应用的修改草稿？
2. 用户是否理解“关键词覆盖”与“候选人能力”的区别？
3. 哪些简历字段最敏感，用户能接受怎样的处理说明？
4. 当前用户在哪一步花费时间最多？
5. 用户判断建议“有用”的标准是什么？
6. 哪些功能不影响核心闭环，可以从公开 Beta 隐藏？
7. 哪些质量错误会直接伤害用户求职结果？

### 4.3 关键活动

#### A. 现有证据整理

产品 Agent 将现有约 20 名试用者反馈整理为统一记录，至少包含：

- 用户目标岗位；
- 原流程用时；
- 使用产品后的流程用时；
- 采用了哪些建议；
- 未采用哪些建议及原因；
- 是否发现误判或编造；
- 是否愿意上传真实简历；
- 是否愿意再次使用。

“平均节省 15–20 分钟”只能标记为小样本自报反馈，不得包装为严格实验结论。

#### B. 用户旅程审计

逐步检查：

1. 访问首页；
2. 理解产品能力边界；
3. 粘贴 JD；
4. 选择并上传简历；
5. 等待分析；
6. 理解要求与证据；
7. 处理缺口和不确定项；
8. 接受、修改或拒绝建议；
9. 导出；
10. 提交反馈或再次分析。

每一步记录用户目标、阻力、风险、需要的页面状态和对应指标。

#### C. 范围冻结

产品 Agent生成 Must/Should/Could/Won't 清单，由产品负责人批准。进入 G0 后，任何新增需求必须交换掉同等或更大工作量的既有需求，禁止无成本加需求。

### 4.4 Agent 分工

| Agent | 任务 | 输出 |
|---|---|---|
| 产品研究 Agent | 整理反馈、JTBD、旅程和风险 | 需求证据表、用户旅程 |
| 产品 Agent | 定义范围、价值主张和验收口径 | 范围矩阵、需求清单 |
| 数据 Agent | 定义北极星和指标口径 | 指标字典 v1 |
| 风险审查 Agent | 识别误导、隐私和求职决策风险 | 风险清单 v1 |
| 产品负责人 | 做最终取舍 | G0 决策记录 |

### 4.5 交付物

- 用户问题与证据摘要；
- 目标用户和 JTBD；
- 当前/目标用户旅程；
- 首发范围矩阵；
- 北极星指标与指标字典；
- 风险清单；
- G0 决策记录。

### 4.6 G0：需求冻结闸门

同时满足以下条件才可进入方案定义：

- 目标用户和核心 JTBD 只有一个明确版本；
- 首发核心闭环可在一句话内说明；
- Must 与 Won't 清单得到产品负责人确认；
- 所有对外能力表述与实际技术能力一致；
- 北极星指标有明确分子、分母和事件来源；
- P0 风险均有负责人和截止时间；
- 需求文档不存在“尽量”“最好”“体验良好”等不可验收表达。

## 5. 阶段二：定义方案（Day 2）

### 5.1 阶段目标

把需求转化为可以独立开发、测试和验收的产品方案，冻结页面状态、接口契约、质量定义、数据边界和发布标准。

### 5.2 方案原则

1. 证据优先：先展示原文证据，再展示判断和建议。
2. 不确定性显式：无法判断时输出“不确定”，不强行给分。
3. 用户控制：任何修改建议必须允许接受、编辑和拒绝。
4. 数据最小化：不保存原始简历，不将正文发送到监控和埋点。
5. 移动优先：390px 宽度必须完成核心流程。
6. 渐进披露：首屏只展示结论、证据和下一步，不一次性堆满 24 项表格。
7. 可降级：非核心模块故障不能阻断核心分析和导出。

### 5.3 目标用户流程

```text
首页与能力边界
  ↓
粘贴一个 JD
  ↓
上传 PDF / DOCX / TXT 简历并同意处理说明
  ↓
前端校验（类型、大小、必填）
  ↓
服务端校验与文本解析
  ↓
JD 要求结构化（必需 / 加分 / 未识别）
  ↓
简历证据匹配（有证据 / 不确定 / 无证据）
  ↓
事实保护型 Bullet 建议
  ↓
用户接受 / 修改 / 拒绝 / 补充事实
  ↓
导出 Markdown 草稿
  ↓
提交有帮助/无帮助反馈
```

### 5.4 页面与状态

#### P1：首页/输入页

必须包含：

- 一句话价值主张；
- “不会预测录用结果”的能力边界；
- JD 文本输入；
- 文件选择和拖拽上传；
- 支持格式、大小和页数说明；
- 隐私处理摘要及详细链接；
- 未默认勾选的用户同意；
- 主 CTA“分析这份简历”；
- 示例 JD/示例简历入口；
- 加载、禁用、失败和重试状态。

#### P2：分析结果页

信息优先级：

1. 识别到的岗位和低置信提示；
2. JD 要求数量和关键词覆盖摘要；
3. 必需要求列表；
4. 每项要求对应的简历原文证据；
5. 不确定项；
6. 未发现证据的要求；
7. 修改建议入口。

不得展示“简历可信度 94”“面试准备度 20”等超出能力范围的指标。

#### P3：修改与确认页

每条建议必须显示：

- 简历原文；
- 建议版本；
- 建议理由；
- 对应 JD 原文；
- 使用了哪些已确认事实；
- 是否包含待确认内容；
- 接受、编辑、拒绝三个动作；
- 用户补充数字或背景的输入框。

带待确认内容的建议不得默认进入导出。

#### P4：导出与反馈页

- 汇总已接受和已编辑建议；
- 显示未确认项数量；
- 导出 Markdown；
- 提醒用户进行最终人工检查；
- 提交“有帮助/一般/无帮助”及可选原因；
- 开始分析下一岗位。

#### P5：隐私和说明页

- 收集什么；
- 为何处理；
- 在哪里处理；
- 是否保存；
- 使用哪些基础设施和第三方资源；
- 日志和监控不记录什么；
- 联系方式；
- Beta 能力边界；
- 用户如何反馈或请求删除已持久化数据（公开 Beta 默认不持久化原文）。

### 5.5 功能需求与验收标准

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-01 | 输入 JD | 50–20,000 字；少于 50 字给出可理解提示；不得静默分析空 JD |
| FR-02 | 上传简历 | 仅 PDF、DOCX、TXT；最大 5 MB；PDF 最大 10 页；不再声明支持旧 `.doc` |
| FR-03 | 真实类型校验 | 扩展名、MIME、文件魔数一致；伪造扩展名返回结构化 4xx |
| FR-04 | 隐私同意 | 未同意时提交按钮不可用；同意不得默认勾选 |
| FR-05 | 文本解析 | 解析为空、损坏、加密或扫描件时给出不同错误和下一步建议 |
| FR-06 | JD 拆解 | 每项要求必须带 JD 原文；区分必需、加分、未知 |
| FR-07 | 证据匹配 | 每个“有证据”结论必须返回简历原文片段；否定表达不得算正向证据 |
| FR-08 | 不确定项 | 只出现相关词但无法证明经历时标记不确定，不计为已覆盖 |
| FR-09 | 修改建议 | 不增加未确认数字、职责、工具、结果和所有权；新增内容必须标记待确认 |
| FR-10 | 用户确认 | 接受、编辑、拒绝结果保存在当前浏览器会话；刷新前有离开提醒 |
| FR-11 | 导出 | 只导出已接受或用户编辑的内容；导出前列出未确认项 |
| FR-12 | 反馈 | 反馈事件不包含 JD 和简历原文；失败不阻断导出 |
| FR-13 | 语言 | 本周期只承诺中文；英文入口隐藏，避免混合语言结果 |
| FR-14 | 响应式 | 390×844、768×1024、1440×900 均能完成核心流程且无页面级横向滚动 |

### 5.6 分析结果定义

#### 不再使用的概念

- 岗位匹配概率；
- 录用概率；
- 简历真实性；
- 面试表现预测；
- ATS 实际排名。

#### 使用的概念

- `jd_requirement_count`：系统识别的 JD 要求数；
- `known_requirement_count`：知识库或规则可识别的要求数；
- `unknown_requirement_count`：无法可靠归一化的要求数；
- `evidenced_count`：简历中找到正向原文证据的要求数；
- `uncertain_count`：相关但证据不足或上下文不明确的要求数；
- `missing_evidence_count`：未发现证据的要求数；
- `keyword_coverage`：`evidenced_count / known_requirement_count`，必须和未知项数量同时展示；
- `analysis_confidence`：只表示解析和规则覆盖信心，不表示候选人水平。

### 5.7 规则与评测方案

#### 最小评测集

公开 Beta 前至少准备 150 个固定用例，其中 30 个为产品负责人亲自复核的金标准用例，120 个可由评测 Agent 生成并由另一个独立评测 Agent 交叉审查。证据准确率等对外质量判断以金标准用例为准，Agent 自生成、自标注的样本只用于扩大回归覆盖，不能单独证明产品准确性。

用例结构如下：

- 50 个正常中文 JD/简历对；
- 20 个英文或中英混合输入；
- 20 个否定、未使用、计划学习等反例；
- 20 个关键词堆砌或技能列表无经历反例；
- 20 个文件解析边界用例；
- 10 个跨岗位或岗位识别冲突用例；
- 10 个事实编造与待确认用例。

#### 标注字段

- 岗位类别；
- JD 原文要求；
- 必需/加分；
- 规范化技能；
- 简历证据片段；
- 证据状态；
- 否定状态；
- 修改建议是否可用；
- 是否新增未确认事实。

#### 质量闸门

- 证据准确率 ≥95%；
- 否定测试 100% 通过；
- 未确认事实编造率 0%；
- 关键词堆砌不能获得“全部已覆盖”；
- 每次知识库或规则更新必须运行冻结评测集并记录版本差异。

### 5.8 API 契约

核心接口：`POST /api/v1/analyses`

请求：

- `jd`: string；
- `resume`: PDF/DOCX/TXT；
- `role`: auto/ai_product/ai_agent/ai_ops；
- `locale`: 固定 `zh`；
- `privacy_consent_version`: string；
- `client_request_id`: UUID。

成功响应至少包含：

- `analysis_id`：短期会话内标识，不关联身份；
- `algorithm_version`；
- `knowledge_base_version`；
- `role`、`role_confidence`；
- `requirements[]`；
- `coverage_summary`；
- `rewrite_suggestions[]`；
- `warnings[]`；
- `processing_ms`。

每个 `requirements[]` 条目包含：

- `requirement_id`；
- `label`；
- `priority`：required/preferred/unknown；
- `jd_evidence`；
- `resume_status`：evidenced/uncertain/not_found；
- `resume_evidence[]`；
- `reason`。

错误响应统一包含：

- `ok: false`；
- `error_code`；
- `message`；
- `request_id`；
- `retryable`；
- `supported_action`。

HTTP 状态码：

- 400：字段或业务输入不合法；
- 413：文件过大；
- 415：不支持的真实文件类型；
- 422：文件可接收但无法解析；
- 429：频率超限；
- 500：未预期服务端错误；
- 503：依赖或服务暂时不可用；
- 504：分析超时。

### 5.9 隐私与安全设计

- 原始文件只在当前请求内存中处理，不写数据库、对象存储或应用日志；
- 请求完成后释放文件和解析文本引用；
- 日志只记录请求 ID、文件类型、文件大小、耗时、错误码和规则版本；
- 文件名不进入日志，因为文件名可能含姓名；
- 监控不得采集请求体、响应正文、JD、证据片段或修改建议；
- 前端第三方 CDN 改为固定版本并优先随站点打包；
- CORS 限制到正式站点域名；
- 增加 CSP、`X-Content-Type-Options`、`Referrer-Policy`、`frame-ancestors` 和最小权限策略；
- 每 IP 建议限制为每小时 10 次分析、同时最多 2 个请求；
- 单请求应用层超时 20 秒；
- 解析器对 PDF 页数、DOCX 解压大小和压缩比设置硬限制；
- 公开说明 Vercel 等实际基础设施提供方，不使用“完全本地”或“无第三方处理”等不准确表述。

### 5.10 非功能需求

| ID | 类别 | 要求 |
|---|---|---|
| NFR-01 | 可用性 | 公开 Beta 核心接口目标可用性 ≥99% |
| NFR-02 | 性能 | TXT/DOCX p95 ≤8 秒，PDF p95 ≤12 秒 |
| NFR-03 | 容量 | 单实例异常不得导致持续不可用；超限请求快速失败 |
| NFR-04 | 可访问性 | 键盘可完成核心流程；表单有 label；错误与状态不只依赖颜色 |
| NFR-05 | 响应式 | 390px 无页面级横向滚动；侧边导航默认关闭 |
| NFR-06 | 兼容性 | 当前稳定版 Chrome、Safari、Edge；iOS Safari 和 Android Chrome 抽测 |
| NFR-07 | 可观测性 | 每个请求有 request ID；错误率、耗时、错误码和版本可聚合 |
| NFR-08 | 可回滚 | 上一个稳定部署可在 10 分钟内恢复 |
| NFR-09 | 可复现 | Python 3.12、锁定依赖、一条命令运行测试和本地服务 |

### 5.11 G1：方案冻结闸门

- 页面、状态和用户动作定义完整；
- FR/NFR 均有可验证标准；
- API 契约由前端、后端和 QA Agent 共同确认；
- 埋点不包含 PII 或正文；
- 隐私数据流通过安全隐私 Agent 审查；
- 评测集结构和质量门槛冻结；
- 本周期隐藏功能已从导航和对外文案移除；
- 产品负责人签署 G1 决策记录。

### 6.4 Agent 任务卡模板

每个任务必须按以下格式派发：

```markdown
任务 ID：
目标：
用户价值：
范围内：
范围外：
```

不允许使用“优化一下”“完善体验”“按最佳实践处理”等无边界任务描述。

### 6.5 Agent 交接协议

每次交接必须提供：

- 变更目的；
- 修改文件；
- 接口或数据结构变化；
- 运行过的验证命令及完整结果；

- 已知风险；
- 需要下一 Agent 继续处理的具体问题；
- 回滚方法。

接收 Agent 必须重新读取相关文件和契约，不得只依赖上一个 Agent 的总结。

### 6.6 变更控制

- G1 后新增 Must 需求必须由产品负责人批准；
- 新增需求必须明确替换或删除哪个当前任务；
- API 契约变更必须同步前端、后端、QA 和文档；
- 算法/规则变更必须增加对应评测用例；
- 隐私数据流变更必须重新经过安全隐私审查；
- Day 5 中午后进入代码冻结，只接受 P0/P1 发布阻断修复。

### 6.7 开发完成定义（Definition of Done）

一个任务只有同时满足以下条件才算完成：

- 实现与确认的需求一致；
- 新增或更新自动化测试；
- 测试命令实际运行且结果可核查；
- 没有把 JD、简历或 PII 写入日志/埋点；
- 错误、空态、加载态和移动端已处理；
- 文案符合公开 Beta 能力边界；
- 独立审查 Agent 通过；
- 无未说明的兼容性或迁移影响。

### 6.8 G2：代码完成闸门

- Must 范围全部满足 DoD；
- 单元、契约和核心 E2E 在 CI 中通过；
- 冻结评测集达到质量门槛；
- 移动端核心流程通过；
- 隐私和安全 P0 已清零；

## 7. 阶段四：上线验证（Day 6–7）

### 7.1 阶段目标

证明发布候选版本在真实生产环境中满足核心功能、质量、安全、性能、隐私、监控和回滚要求，并由产品负责人做最终 Go/No-Go 决策。

### 7.2 测试矩阵

| 测试层 | 主要覆盖 | 发布阻断条件 |
|---|---|---|
| 单元测试 | 解析、规则、否定、证据、事实保护 | Must 路径失败 |
| API 契约 | 状态码、字段、版本、错误码 | 前后端契约不一致 |
| E2E | 上传→分析→确认→导出 | 任一核心步骤无法完成 |
| 移动端 | 390px、iOS Safari、Android Chrome | 遮挡、溢出、无法操作 |
| 文件 | PDF/DOCX/TXT、损坏、加密、扫描、超限 | 非法文件导致 500 或资源异常 |
| 对抗 | 否定、关键词堆砌、无经历技能列表 | 产生全覆盖或权威高分 |
| 安全 | 伪造类型、压缩炸弹、限流、CORS、安全头 | 可绕过限制或泄露正文 |
| 隐私 | 日志、埋点、监控、错误响应 | 出现 JD、简历或 PII |
| 性能 | 冷启动、正常请求、接近上限文件 | p95 超门槛且无降级方案 |
| 可访问性 | 键盘、label、焦点、错误提示 | 无法完成核心流程 |

### 7.3 生产验证步骤

1. 部署发布候选版本到预览环境；
2. 运行完整自动化测试；
3. QA Agent 按 FR/NFR 手动验收；
4. 安全隐私 Agent 查看生产配置和响应头；
5. 评测 Agent运行冻结评测集；
6. 部署到生产但暂不主动导流；
7. 验证首页、健康接口和完整分析 smoke test；
8. 检查监控是否收到成功、失败、耗时和版本数据；
9. 使用非敏感合成简历验证导出；
10. 以 5–10 名已知用户进行短时灰度；
11. 观察 2 小时错误率、失败原因和反馈；
12. 产品负责人做 G4 决策；
13. Go 后开放公开入口并持续值守。

### 7.4 监控与告警

必须监控：

- 首页和健康接口可用性；
- 分析请求量；
- 分析成功率；
- 4xx/5xx/429/504 分布；
- 按文件类型的解析失败率；
- p50/p95/p99 耗时；
- 当前算法和知识库版本；
- 导出成功率；
- 反馈分布；
- 限流触发量。

建议告警：

- 5 分钟内健康接口连续 3 次失败；
- 15 分钟分析成功率低于 95%；
- 15 分钟服务端 5xx 高于 2%；
- p95 连续 15 分钟超过 15 秒；
- 单一错误码占失败请求 50% 以上；
- 日志或监控检测到疑似邮箱、电话等 PII 模式。

### 7.5 回滚策略

- 保留上一个验证通过的部署；
- 回滚目标时间 ≤10 分钟；
- 新规则通过 `algorithm_version` 可切回上一版本；
- 非核心建议模块可通过开关关闭，保留 JD 拆解和证据结果；
- 分析服务异常时首页显示维护状态，禁止用户继续上传；
- 回滚后由产品负责人发布简短状态说明并记录事故。

### 7.6 Go/No-Go 决策表

#### 必须 Go 条件

- 核心 E2E 全部通过；
- 390px 移动端无页面级横向滚动；
- 评测达到证据、否定和编造门槛；
- 文件限制、限流和超时有效；
- 隐私、条款、联系方式上线；
- 埋点和监控不含正文与 PII；
- 生产监控和告警有效；
- 回滚演练完成；
- 所有 P0 清零；
- 产品负责人明确批准。

#### 必须 No-Go 条件

- 否定表达仍会被当作正向能力；
- 关键词堆砌仍产生“完全匹配”结论；
- 移动端无法完成上传或查看结果；
- 原始简历出现在日志、监控或埋点；
- 超大或伪造文件可以绕过限制；
- 核心接口没有可用监控或回滚；
- 公开文案仍宣称离线处理、无第三方上传或预测录用；
- 发布候选版本的测试结果不可复现。

### 7.7 G3/G4 闸门

- G3：QA、安全、评测三方独立签署发布候选版本通过；
- G4：产品负责人依据 Go/No-Go 表做最终公开决定；
- Agent 无权在 P0 未清零时自行降低优先级或发布。

## 8. 阶段五：数据迭代（Day 7 起）

### 8.1 阶段目标

用真实行为、质量和故障数据验证核心价值，优先解决阻断和高频低价值问题，不在首周立即恢复被隐藏的功能。

### 8.2 事件字典

| 事件名 | 触发时机 | 允许属性 | 禁止属性 |
|---|---|---|---|
| `page_viewed` | 首页加载 | 页面、来源类别、设备类别 | URL 查询中可能含 PII 的原值 |
| `analysis_started` | 合法提交分析 | 文件类型、文件大小区间、JD 长度区间、规则版本 | JD、文件名、简历正文 |
| `upload_validation_failed` | 前后端拒绝文件 | 错误码、类型、大小区间 | 文件名、正文 |
| `analysis_succeeded` | 返回成功 | 耗时、要求数、状态计数、版本 | JD、证据和建议正文 |
| `analysis_failed` | 返回失败 | 错误码、耗时、可重试 | 异常中的请求体或正文 |
| `evidence_viewed` | 展开证据 | requirement_id、状态 | 证据文本 |
| `suggestion_accepted` | 接受建议 | suggestion_id、版本 | 原文与建议正文 |
| `suggestion_edited` | 编辑建议 | suggestion_id、是否补充事实 | 用户编辑内容 |
| `suggestion_rejected` | 拒绝建议 | suggestion_id、原因枚举 | 自由文本中的简历内容 |
| `draft_exported` | 导出成功 | 格式、建议数量、未确认数量 | 导出正文 |
| `feedback_submitted` | 提交反馈 | 评分、原因枚举 | 默认不采集自由文本；开放时需提示勿填 PII |

### 8.3 分析看板

看板按四层组织：

1. 流量：访问、来源、设备；
2. 漏斗：开始分析、成功、查看证据、采用建议、导出；
3. 质量：证据反馈、误判类型、编造问题、规则版本；
4. 稳定性：错误、文件解析失败、延迟、限流和可用性。

所有比率必须同时展示分子、分母和样本量。样本不足 30 时不做显著趋势结论。

### 8.4 上线后节奏

#### 首 2 小时

- 产品负责人和监控 Agent 持续值守；
- 每 30 分钟检查错误率、p95、解析失败和 PII 告警；
- P0 立即回滚或关闭上传；
- 不进行功能新增。

#### 首 24 小时

- 汇总漏斗和前 10 个失败原因；
- 人工抽查至少 20 个合成/经授权结果；
- 分类所有反馈；
- 形成首日问题清单；
- 只发布 P0/P1 修复。

#### 72 小时

- 比较移动端与桌面端完成率；
- 分析上传失败、解析失败和建议拒绝原因；
- 回看规则版本质量；
- 决定是否扩大流量或保持 Beta 提示；
- 不因访问量增长直接恢复非核心功能。

#### 第 7 天

- 复盘北极星、激活、质量、留存和稳定性；
- 形成继续、修正或停止三类决策；
- 更新产品路线图；
- 只有数据证明核心闭环稳定后，才评估 OCR、多 JD、英文、学习路线、模拟面试或账号。

### 8.5 反馈分类

| 类别 | 示例 | 优先级原则 |
|---|---|---|
| 事实风险 | 建议编造经历、把否定当肯定 | P0，立即处理 |
| 隐私安全 | 正文进入日志、限制可绕过 | P0，立即回滚/关闭 |
| 核心阻断 | 无法上传、结果空白、无法导出 | P0/P1，按影响面处理 |
| 质量问题 | 要求漏识别、证据不准确、建议不可用 | 按频率×严重度排序 |
| 体验问题 | 信息太多、移动端难读、文案不懂 | 进入近期迭代 |
| 功能请求 | OCR、账号、更多岗位 | 不自动进入开发，先验证需求频率 |

### 8.6 迭代优先级公式

采用简化 ICE：

> 优先级 = 用户影响（1–5）× 发生频率（1–5）× 证据可信度（0.5–1.0）÷ 实现成本（1–5）

但以下问题不参与公式，直接最高优先级：

- 事实编造；
- 隐私泄露；
- 安全绕过；
- 核心服务不可用；
- 无法回滚；
- 对用户产生重大误导的评分或文案。

### 8.7 G5：继续放量闸门

继续扩大公开流量必须满足：

- 连续 72 小时无 P0；
- 分析成功率 ≥98%；
- 5xx <1%；
- 事实编造率为 0；
- 证据准确率维持 ≥95%；
- 有效建议采用率达到或接近 30%，且样本量足以解释；
- 移动端完成率没有显著落后；
- 用户反馈中没有系统性隐私或误导问题。

## 11. 产品负责人每日决策清单

### Day 1

- 是否只保留一个核心闭环？
- 是否明确隐藏非核心功能？
- 是否接受“关键词覆盖”替代“匹配度”的对外口径？
- 是否确认公开 Beta 的成功指标？

### Day 2

- 页面、接口和验收是否没有歧义？
- 隐私与数据流是否能够公开解释？
- 是否有足够评测用例阻止错误高分？

### Day 3–4

- Agent 是否遵守冻结契约？
- 是否出现未经批准的范围扩张？
- 核心 E2E 是否真实跑通，而非只看代码？

### Day 5

- P0 是否全部进入测试验证？
- 是否可以冻结代码？
- 是否有独立 Agent 审查，而非开发者自报通过？

### Day 6

- 是否有完整测试和评测证据？
- 是否完成生产环境和回滚演练？
- 是否仍存在无法解释的评分、隐私或移动端问题？

### Day 7

- 灰度 2 小时是否稳定？
- 是否需要延迟、降级或回滚？
- Go 决策是否基于证据，而不是因为“已经到第七天”？

## 15. 实施计划的输入边界

后续实施计划必须基于本文件，并遵守以下优先顺序：

1. 用户与事实安全；
2. 隐私与上传安全；
3. 移动端核心闭环；
4. 证据和修改建议质量；
5. 自动化、监控和回滚；
6. 性能与体验；
7. 非核心功能。

若一周内资源不足，按顺序从第 7 项向上削减。不得通过删除前五项来保证日期。
